# 集结房间（Gathering Room）产品需求文档

> 日期：2026-08-07
> 状态：Phase A · 产品方向已定稿（founder + 顾问），本文档为可实现 PRD；场景美术见 `docs/design/lovart-brief-gathering-room.md`；形象直接复用现有 V2 纸娃娃与装备体系，不再新建 SD 像素形象。2026-08-10：房间场景合成图（`room-composite-v2.webp`，2026-08-27 窗框修复；v1 保留作回滚）已落地，`ROOM_ART_READY` 切换为 `true`，CSS 占位房间退化为降级兜底。
> 范围：微信小程序（唯一在发用户端）。MVP 明确不做的事项见 §7，不做扩张

## 1. 定位

集结房间是**一场真实线下活动的线上前厅**。

它不是虚拟世界、不是聊天室、不是游戏大厅。它是「我们周六要去的那家小店」的预告片：匹配成功后，6 个还没见过面的人提前几天陆续「走进」同一间暖木小店，看到自己 V2 形象（带装备）坐在桌边，看到队友一个个推门进来，直到活动当天在真实的店里认出彼此。

一句话：**把焦虑的等待，变成期待的等待。**

现状里，用户报名、付款、匹配成功之后到活动当天之间是一段沉默期——不知道队友是谁、不知道局会不会黄、容易产生「我是不是买了个寂寞」的焦虑。集结房间把这段沉默期变成有生命力的候场：房间每天都在变化（队友到场、桌面从订位卡变成餐具），等待本身成为体验的一部分。

**装备展示语境：** 用户的装备（头部配饰 + 上装/下装/鞋，完整沿用现有装备体系）在房间里被**人生中最重要的 5 个观众**看到——同一张桌子的 5 位队友。这不是陌生人广场上的展示位，而是即将同桌吃饭的人提前看到你的样子，装备的社交价值在这个语境里最大化。

## 2. 生命周期

| 阶段 | 触发 | 房间状态 |
|---|---|---|
| 生成 | 匹配完成（成局）时自动创建 | 房间就绪，全部座位「虚位以待」 |
| 活跃 | 生成后 → 活动开始 | 三态在场系统、入场编排、桌面逐日演化（订位卡 → 餐具） |
| 记忆页 | 活动结束后 | 定格为回忆页：全员合影 + 装备定格（活动当天大家穿的那身），可查看、可分享 |
| 关闭 | 记忆页保留期结束后 | 房间关闭，不再可进入；记忆页内容沉淀到用户足迹语境 |

关键约束：房间的生命周期完全由**真实活动的状态机**驱动，不做独立的生命周期管理。活动成行则房间活跃，活动结束则房间定格，活动取消/未成行则房间随退款流程一并关闭（该路径 Phase A 不做特殊美术，走现有通知体系）。

## 3. 三态在场系统

房间的权威数据源是**真实用户行为**，不是匹配结果原子状态。每个座位上的队友处于且仅处于以下三态之一：

| 状态 | 判定（source of truth） | 房间内表现 |
|---|---|---|
| **未现身** | 已匹配入组，但从未打开过房间页面 | 座位上放**名牌/剪影**占位，叙事框架为「正在路上」——不是缺席，是还没到 |
| **在场** | 打开过房间（建立短暂的 WebSocket presence，离开页面即消失） | V2 形象出现在自己座位，带待机呼吸动画（沿用既有生理呼吸节奏，RM 抑制） |
| **已确认出席** | 显式确认：调用现有 `POST /api/pool-groups/:groupId/confirm-attendance`（`apps/server/src/routes/domains/userEventPools.ts:1733`） | V2 形象**入座**到自己的座位（从站到坐的姿态切换），状态持久 |

设计要点：

- **「在场」是 ephemeral 的**——WS presence 断开即回到「未现身」的持久判定基线；已确认出席是唯一持久化的到场信号，且复用现有接口，不新建确认通道。
- 三态的视觉差异必须让「这个局在一点点变真」可读：剪影 → 站着的小人 → 坐定的小人，是一个叙事后退不可能的状态机（确认不可逆）。
- 「未现身」永远不说「没来」「缺席」「未读」这类冷词；统一「正在路上」框架（详见 §6 空房间失败模式）。

## 4. 入场编排（Entry Choreography）

入场是房间的核心情感时刻，按到达次序编排：

1. **第一个到达者：** 触发「你是第一个到的」叙事时刻——空房间、只为你亮着的那盏灯，附带一个小特权：**挑选自己的座位 / 摆放第一件桌面小装饰**（二选一，实现期定；特权必须轻，不影响他人体验）。
2. **后续到达者：** 推门走进来动画（门图层开门 → 角色走入 → 落位）；**已经在场的形象抬头看一眼**再回去——一个「有人来了」的微交互，让先到的人感知到房间的活。
3. **补位（匹配后加入的新队友）：** 走同一套新人入场动画 + 触发一条站内通知钩子（复用现有 in-app notification 体系，见 §7 非目标中的订阅消息边界），文案方向「有新队友推门进来了」。

## 5. 最小交互集

MVP 只有两种交互，都做透：

| 交互 | 行为 | 产出 |
|---|---|---|
| **点按形象** | 点队友的 V2 形象 | 弹出**同桌卡**：原型（12 原型中文名，如「脑洞章鱼」）/ 装备 / topInterests（沿用现有兴趣数据）。这是破冰的前置——活动前就知道同桌是谁、对什么感兴趣 |
| **戳一戳** | 对队友形象 poke | 对方收到一个 emoji 反应（经 `JoyJoinIcon` 图标体系渲染，不用内联 emoji）；轻量、无对话压力 |

## 6. 空房间与低占用失败模式

**房间永远不许是「冷的空房间」。** 空房间的叙事框架是**虚位以待的悬念感**：灯是暖的、桌布是铺好的、名牌是摆好的——这是一个「在等人」的房间，不是一个「没人」的房间。

| 占用 | 渲染 |
|---|---|
| 0/6（刚生成，无人到过） | 完整场景 + 6 张名牌剪影 + 桌面订位卡；文案氛围「店已经订好了，大家在路上」 |
| 1/6 | 第一个到达者的形象 + 5 张名牌剪影；「你是第一个到的」叙事时刻（§4-1） |
| 4/6 | 多数已就位：已到者入座/站立 + 剩余 2 张名牌剪影；悬念集中在「还差谁」 |
| 6/6 | 全员到齐（全员已确认出席）→ 全员庆祝时刻（§9） |

低占用时段（如前 24 小时无人进房）不做 push 催促 MVP；房间自身的视觉状态就是提醒。

## 7. 非目标（MVP 明确不做）

以下每一项都是深思熟虑后的排除，Phase A 不做、不留半成品入口：

- **不做行走 / 4 方向移动。** 角色只有正面朝向（风格规范 T5），4 方向转身图明确延期。房间内没有虚拟摇杆、没有走位。
- **不做聊天。** 房间内没有任何文字/语音交流能力。破冰交给活动当天的 Social Icebreaker 与同桌卡的兴趣信息。
- **不做三档皮肤。** 破冰局 / 畅聊局 / 狂欢局的房间皮肤延期到 Phase 2；但场景分层结构必须为换肤预留（见 `docs/design/lovart-brief-gathering-room.md` 的结构约束）。
- **不做微信订阅消息的服务端下发。** 补位、全员确认等钩子只走站内通知（in-app notification）；订阅消息（subscribe-message）的服务端发送链路不在本期范围。

## 8. 埋点与度量

**北极星指标：到场率（真实活动到场率）。** 集结房间存在的全部理由是让更多人真的出现在周六晚上的店里。到场率基线正在独立埋点建设中（另行立项），本功能上线后对比基线。

**护栏指标：成局率不降。** 房间不得对匹配/报名主流程产生任何负向影响（性能、报名转化、取消率均纳入观察）。

功能埋点（snake_case，沿用现有 analytics 体系）：

| 事件 | 含义 |
|---|---|
| `room_entered` | 进入房间（区分首进/回访；首进触发「第一个到的」判定） |
| `room_poke` | 戳一戳（携带双方原型 metadata） |
| `room_confirm_attendance` | 在房间内完成出席确认（与现有 confirm-attendance 接口打通归因） |
| `room_all_present` | 全员庆祝时刻曝光（6/6 已确认） |

辅助观察：房间打开率（匹配用户中进过房间的比例）、同桌卡查看率、记忆页回访率。

## 9. 全员确认时刻

6/6 已确认出席时触发**全员庆祝时刻**：房间内庆祝动画（全员形象同框 + 灯光变化，具体表现实现期定稿，RM 降级为静态帧）+ 一条站内通知（「你们这桌人齐了」）。这是房间活跃期的情感峰值，也是「预告片」的最后一幕——下一幕就是线下见。

## 10. 商业语境摘要

- **焦虑等待 → 期待等待：** 付费到活动之间的沉默期是退款与流失的高发段。房间把这段时间填充为逐日演化的期待（队友陆续到、桌面从订位卡变成餐具），让用户感到「我买的不是一个名额，是一个正在成形的局」。
- **装备的 5 个最重要观众：** 装备体系（`equipmentRewardsEnabled`）此前主要在个人 Profile 自我欣赏。房间给了装备一个真实社交语境：同局的 5 位队友会在活动前几天就看到你的形象。装备的获取动机（活动手动抽取、碎片兑换）因此获得展示闭环，且全程无支付商店、无攀比排行——符合现有权益体系基调。
- **记忆页的长尾价值：** 活动后定格的合影 + 装备定格是可分享的物料（沿用现有 Canvas poster 管线约束），让一场已成行的局在活动结束后继续产出传播素材。
- **与三档局的关系：** 本期房间对破冰局 / 畅聊局 / 狂欢局完全同构；Phase 2 的三档皮肤才是差异化载体，本期不为此做任何分支逻辑。

## 11. 发布形态与技术边界

- **页面位置与开关：** 房间页面独立成包，落在 `pages/gathering-room` 子包，整体挂在新特性开关 `gatheringRoomEnabled`（**默认 false**）后面。开关关闭时，入口不出现、页面不可达、相关查询不发起（对齐 Profile V1.7「关闭即不发请求」的降级纪律）。开关按 `feature-flags-launch-config` 规范走 DB 旗标 + env 兜底，经 `/api/auth/user` 下发客户端。
- **场景美术（`ROOM_ART_READY`）：** Lovart 像素场景已交付为单张合成 WebP（`room-composite-v2.webp`，750×960 px，82 KB；2026-08-27 窗框错位修复后重新合成，v1 保留作回滚），运行时以 `ROOM_ART_READY = true` 渲染。组件仍保留 CSS 占位房间作为降级路径（CDN/本地图片均失败时），两版共用同一套座位锚点坐标，角色层代码无需改动。
- **运行时约束：** 整数倍缩放、风格防火墙、分层合成以 `docs/design/sd-pixel-avatar-style-guide.md` T6/T7 与场景 brief 为准；子包 WXSS 拆分遵守既有 `verify:subpackage-styles` 纪律（页面 SCSS `@use` 组件 SCSS）。

## 12. 依赖与边界

| 依赖 | 现状 |
|---|---|
| `POST /api/pool-groups/:groupId/confirm-attendance` | 已存在，直接复用 |
| 装备 inventory / 穿戴数据 | 已存在（Profile 我的形象体系）；房间内直接渲染完整 V2 形象 + 全部已穿戴装备 |
| WebSocket presence | 复用现有 WS 基础设施的房间广播能力（`websocket-realtime`） |
| 站内通知 | 复用现有 notification 体系（`notification-system`） |
| 场景美术 | 本 Phase 配套 Lovart brief 产出中；像素场景落地前由 CSS 占位房间过渡（§11 `ROOM_ART_READY`）。形象复用现有 V2 纸娃娃 + 装备体系，不再新建 SD 像素形象 |
| 分享物料（合影 / 记忆页定格） | 沿用 Canvas poster 管线（DPR ≤2、CDN PNG 兜底） |
| 特性开关 | `gatheringRoomEnabled`（DB 旗标，默认 false，见 §11） |
