**Matching:** `poolMatchingService.ts` is deterministic authority. 6D scoring (chemistry, interest, socialAffinity, backgroundDiversity, preference, language). Optional 7th semantic dimension behind `ENABLE_SEMANTIC_SIMILARITY`. AI may enrich explanations but **must not** redefine scoring. Feature-flagged operator-review gate (`matchingOperatorReviewEnabled`) holds formed groups in a pending admin-review state before post-match side effects run; users continue to see the normal pending flow until an operator approves. **Explanation normalization (2026-07-13):** `matchExplanationService.ts::normalizePairExplanationText` is the authoritative normalizer applied at generation (`parsePairExplanationContent`), persist (`savePairExplanationsCache`), and serve (`generateGroupAnalysis` — legacy cached rows cleaned on read), guaranteeing stored/served explanations are plain text, never `{`/`[`-leading (the old catch fall-through had persisted truncated/fenced LLM JSON verbatim). Generation-boundary salvage logs `logger.warn('[MatchExplanation] recovered malformed explanation payload', { promptVersion: 'pair-explanation-v3', kind: truncated|fenced|nested|missing-key, recoveredLength })`; serve/persist paths stay silent. **Shared highlights (2026-08-03, pair-explanation-v3):** `findSharedSignalHighlights` adds deterministic 共同点 one-liners (共同必聊项 level-3/heat-25 → 共同有效 intent → 同乡, ≤3, deduped against connectionPoints) to `MatchExplanation.sharedHighlights`, injected into the prompt facts block and rendered above the LLM prose in matching-status `UnifiedRevealCard`; pair cache `schemaVersion` bumped 2→3 (old rows lazily invalidated). Client defense-in-depth: `normalizeMatchingCopy` (`packages/shared/src/features/matching-status/viewModels.ts`, `unwrapTruncatedJsonWrapper` + `extractReadableText` recursion guard) never returns `{`/`[`-leading strings at any nesting depth. Cache: `event_pool_groups.pair_explanations_cache` (JSONB), 7-day TTL. **Gender-balance enforcement (wired 2026-07-14):** previously inert `event_pools` columns are live — `genderBalanceMode` (`none`/`soft`/`hard`, default `soft`), `genderBalanceBonusPoints` (0–100), `minFemaleCount`/`minMaleCount` (0–20). Soft = post-clamp bonus in `calculateGroupDiversity` for exact male/female balance (default-ON is intended 1:1 policy, never blocks formation); hard = floor gate at group commit and in **all three** redistribution phases (failing groups discarded, members returned to candidate pool; floors hard-mode-only; undisclosed gender counts toward neither floor). `genderRestriction="女性"` implies mode `none`. Admin portal pool create/edit (`性别平衡` section) enforces identical POST/PATCH validation (`insertEventPoolSchema.extend` + `updateEventPoolSchema`); PATCH is audit-logged. Spec: `docs/systems/MATCHING_ALGORITHM_REFERENCE.md` §4.2.1.

**Operator-review-gate unmatched bug fix (2026-07-31, commit `e68edc5e8`):** with `matchingOperatorReviewEnabled=true`, `saveMatchResults` step 2 sets matched members to `matchStatus='pending'`, then step 5 marked **all** `'pending'` registrations `'unmatched'` — flipping the just-formed group's members to unmatched (group-fill 0/0, empty 足迹, confirm-attendance 找不到组; also made a formed matching-test group vanish). Step 5 now only marks the truly stranded (`assignedGroupId IS NULL`). Regression lock: `poolMatchingUnmatchedGuard.test.ts`. Note: code default `getFeatureFlag('matchingOperatorReviewEnabled', false)` is `false` but DB/staging run `true`.

**足迹 one-card-per-matched-pool (2026-07-31):** a matched pool dual-writes a legacy `events` row (`<pool> - 第N组`) + per-member `event_attendance` at match-commit (`saveMatchResults` step 2.5) / single-test finalization, and `getUserJoinedEventsSummary` concatenated legacy + pool rows with no dedup — so one matched pool showed a duplicate legacy card whose `events.id` has **no serving detail endpoint** (`loadEventDetail` only handles `/api/event-pools/:id` and `/api/blind-box-events/:id` → 404「加载活动详情没成功」). `joinedEventsRepo` legacy branch now `LEFT JOIN eventPoolGroups ON eventId` and keeps only `IS NULL` (drops match-derived legacy cards; standalone legacy events unaffected). Each matched pool yields one servable pool card. Regression lock: `joinedEventsRepoContract.test.ts`.

**Matching-Test Mode (2026-06-24; updated 2026-07-26):** End-to-end matching validation with one real tester + full-profile bot users through the **same production matching engine**. Defense-in-depth isolation: `isMatchingTestMode()` double gate (requires `ENABLE_SINGLE_TEST_MODE` + `ENABLE_MATCHING_TEST_MODE`; returns false in `APP_MODE=production`), DB markers `users.is_test_bot` + `event_pools.is_test_pool`, and a startup sentinel that crashes if test-bot rows exist in production. Routes at `/api/test/matching-test/*` (start, match, cleanup). Service at `apps/server/src/services/matchingTestService.ts`. Bot profiles include archetypes, industry tiers, `user_interests`, and registration preferences so `poolMatchingService` can score them identically to real users. Groups are finalized into `events`/`blindBoxEvents`/`eventAttendance`/`venueTimeSlotBookings` via `matchingTestService.ts:finalizeTestPoolGroups()` (also reused by `singleTestService.ts`) so post-match flows (event detail, confirm-attendance) work end-to-end. Cleanup preserves payment records. **Test pools are exempt from the registration capacity gate (2026-07-31):** single-test sessions register tester + 5 bots, filling the pool to exactly `maxGroupSize × targetGroups` (6/6) by design — `describePoolRegistrationAvailability` (`apps/server/src/lib/poolRegistrationRules.ts`) skips the `POOL_FULL` check when `event_pools.is_test_pool=true` (threaded through `/register`, `/register-with-payment`, and `payments.ts:resolveEventCheckout`), and the pool_full notification/WS broadcast is skipped for test pools. Real event pools keep the full capacity rule (queues may exceed 6; matching forms groups of 4-6). Regression lock: `poolRegistrationRules.test.ts`. **Client cache bust after single-test start (2026-07-31):** `/api/test/single-test/start` registers the tester server-side as a side effect, so `SingleTestBanner` (`apps/mini-program/src/components/dev/SingleTestBanner.tsx`) runs `bustRegistrationCaches(queryClient)` after start/reset — the shared `REGISTRATIONS_QUERY_KEY` carries `staleTime: 30s`, and without the bust the fresh registration stays invisible on matching-status (missing-registration error state) for up to 30s. **Test-mode cleanup FK cascade (2026-07-31, commit `675ac3624`):** `cleanupSingleTestData` and `cleanupMatchingTestData` used to enumerate child tables by hand before deleting virtual users / test bots, which repeatedly missed new FK dependents (`event_pool_registrations`, `blind_box_events`, etc.) and failed with FK violations. `apps/server/src/lib/fkCascadeDelete.ts` now provides `cascadeDeleteByIds(tx, rootTable, rootColumn, rootIds)` which discovers non-`ON DELETE CASCADE` foreign keys from `pg_constraint` at runtime, recurses deepest-first, and deletes transitive dependents automatically. Future schema additions are covered without code changes. Safety rails: UUID-only root IDs (injection guard), ignores existing `ON DELETE CASCADE` edges (left to Postgres), depth cap + visited-edge set prevents runaway/cycles, schema-qualified table names are taken verbatim from Postgres, columns are quoted. Note: it only walks dependencies that point **at** the root table; reverse references (e.g. `eventPoolGroups.eventId → events.id` from derived legacy events) still require explicit back-link cleanup as in `cleanupSingleTestPoolRows`. Regression lock: `apps/server/src/__tests__/fkCascadeDeleteContract.test.ts`. **Social Icebreaker test mode** is a single-player variant for QA/demoing the session flow: `TestModeDisclosure` pauses the host in `warmup`, and deterministic bot simulation (`apps/server/src/services/socialIcebreakerBotService.ts`) populates all multiplayer phases when `runBots === true`. Docs: `docs/operations/test-mode-operations.md` §H and §I.

**双人成行 Duo registration (2026-08-07; integrity guard 2026-10-24):** Bound duos are hard atomic units in `poolMatchingService.ts`: a duo consumes 2 seats in exactly one group (max 1 duo per group), the duo's unit score is the mean of both members' pair scores, the internal duo pair is excluded from group-quality metrics, and R1 (no isolate with ≥60 strong tie) must hold per member. A valid binding requires both users to hold registrations in the same pool; each user may have at most one valid duo partner per pool, and extra binding requests are rejected without blocking registration/payment. Before group formation, `matching/duoPairResolution.ts` removes every user involved in overlapping pairs from the pair set and logs `duo_conflict`; one-sided hard-constraint survival strands both partners. If a bound duo cannot be placed, the fallback is variant A 整组顺延 — the duo stays unmatched together and flows into the existing 场次未成行 auto-refund pipeline. See `docs/design/duo-registration-spec-20260807.md` and `docs/systems/MATCHING_ALGORITHM_REFERENCE.md` §4.2.2.

**安心补位 Phase 0 — post-reveal seat lifecycle (2026-08-27, commit `37c3e2d89`, both flags ship dark):** User-initiated cancel now runs through the shared orchestrator `apps/server/src/lib/poolRegistrationCancel.ts` (parity across `DELETE /api/pool-registrations/:id` and the blind-box cancel path). Pre-reveal (flag `preRevealRefundEnabled`) = real full refund — money via `claimPaymentForRefund` atomic claim (idempotent; refund failure aborts WITHOUT deleting the registration, retryable), credits via `reverseRedemptionForRegistration` in-transaction BEFORE delete (this also fixed the `event_credit_redemptions` FK 500 on credit-paid cancels). **Matching-status / pool-group-detail 桌友 UI (2026-08-16):** Client presentation of matched members now shares one reusable `TablemateCard` component across the matching-status matched carousel, squad-unboxing front-face reference, and the pool-group-detail deck strip. Pair-chemistry display helpers (`pairChemistry.ts`) centralize the temperature-word, tier emoji, connection-point copy normalization, and interest-hook logic. This is a UI-only unification — scoring and pair explanations remain server-owned.

**排桌 timing guard (2026-11-10):** Early matching is no longer a one-way bet. `poolRealtimeMatchingService.calculateDecayedThreshold` is now a monotonic curve — the bar is strictest far from the event and eases toward `minThresholdAfterDecay` in the final day (7-day ramp capped by `highCompatibilityThreshold`), replacing the previous inverted decay where being far out made matching *easier*. `evaluateEarlyMatchGate` additionally holds automatic scans until the pool is 80% of `targetGroups × maxGroupSize` or `registrationDeadline` is within 48h, recording a `waiting` row in `pool_matching_logs` with the reason; `admin_manual` runs, test pools, and pools without a deadline bypass the gate. Because matching is triggered by registration/payment/admin rather than a clock, `lib/poolDeadlineMatchScheduler.ts` (15-min tick, kill switch `poolDeadlineMatchSweepEnabled`) is the backstop: every active non-test pool past its `registrationDeadline` gets one scheduled scan, and if it still cannot form a table the sweep calls `refundUnmatchedRegistrations` and marks the pool `cancelled` — closing the earlier gap where a pool could sit `active` past its deadline with paid registrations and no refund.

**Late-arrival / orphan registration guarantee (2026-11-11):** a registration can be written into a pool that already left `active` — a WeChat payment webhook landing after 排桌 committed or after the deadline sweep cancelled the pool, or a free registration racing a match run. `scanPoolAndMatch` bails on non-active pools and the refund for that run has already fired, so historically such a row stayed `pending` forever: paid, no group, no refund. Two layers now close it. (1) `repositories/paymentFulfillmentRepo.ts` reads the pool `status` under `FOR UPDATE` before writing the registration and records a `lateClosedPoolId` when it is no longer `active`; the registration is still written (credit reversal and the user's history stay coherent) but `reconcileOrphanRegistrationsForPool` runs right after commit. (2) `lib/poolOrphanRegistrationReconciler.ts` (15-min tick, kill switch `poolOrphanRegistrationSweepEnabled`, 14-day lookback, `isTestPool` excluded) is the backstop: it finds `pending` registrations in non-active pools, flips them to `unmatched`, and routes them through the existing pool-scoped idempotent refund pipeline — `pool_cancelled` copy when the pool was cancelled, `seat_not_allocated` otherwise. `lib/poolCompletionSweep.ts` now calls the same reconciler for every pool it completes, so closing a pool can never strand a paid registration. Both the reconciler and the completion sweep are fail-open per pool and retried on the next tick.

**溢出不是死胡同 (D4, 2026-11-11):** 容量闸 `lib/poolRegistrationRules.ts` 仍然拒绝超出 `maxGroupSize × targetGroups` 的报名，但 `POOL_FULL` 现在携带 `alternatives[]`（`lib/poolOverflowAlternatives.ts`：同城、尽量同区、7 天内、`spotsLeft > 0`、最多 3 个，fail-open 返 `[]`），由免费报名、下单前校验与 `resolveEventCheckout` 三处一并返回。客户端 `useOptimisticRegistration` 的 `onOverflowAlternatives` 把列表交给页面，`PoolRegistrationOverflowAlternatives` 渲染成「这场满了，隔壁还有位置」并 `redirectTo` 目标池——一次点击完成换场，不重填画像、不重选价位、不产生新页面。付费路由 `payments.ts` 的容量校验**保持不变**（支付硬禁区）。候补队列（场次级 FIFO、排到才付、15 分钟确认）**未实现**，只有当换场转化 < 15% 时才考虑。埋点 `overflow_alt_shown` / `overflow_alt_joined` 尚未接入（目标文件被并行的同桌揭晓改动占用）。

**一把尺子：临期准入曲线 (D3, 2026-11-11, flag 默认关):** 逐人准入下限不再固定为 52/60/70，而是与组级时间衰减阈值同源。`matching/matchingCurve.ts` 导出 `calculateDecayedThreshold` 与 `resolvePairFloor(hoursUntilEvent, config)`：`clamp(calculateDecayedThreshold(config.mediumCompatibilityThreshold, h, config) - 13, 45, 65)`。默认配置下，距活动 ≤0/24/48/72/96/120/144/≥168 小时的组阈值为 50/55/60/65/70/75/80/85，对应逐人下限 45/45/47/52/57/62/65/65。`PAIR_OVERALL_GAP = 13` 是 overall 60 附近的局部标定（pair 权重 0.6），不是可逆换算；组级 `overallScore >= currentThreshold` 仍是最终质量闸。R1 无孤立者与 `poolFormation.ts` 的 `strongTieDeficitExempt` 共用同一个 `strongTieThreshold`，flag 开启时临近活动会从 60 跟到同一下限（刻意降标，已披露，不拆第二个 flag）。`pairFloorCurveEnabled` 默认 false，有效暴露 = master &&（`scope=global` 或 `scope=pilot` 且 pool.id 命中 `PAIR_FLOOR_CURVE_PILOT_POOL_ID`）；扫描每次只解析一次，核心不接收时钟或 config。`pool_matching_logs` 写 `pair_floor`，`event_pool_groups` 写 `avg_pair_score` / `formed_member_count` / `pair_floor_policy`（`legacy|curve_v1`；历史 NULL = 未知）。migration `0104_matching_pair_floor.sql` 必须先于代码应用到 staging 和生产。放量前用只读 `GET /api/admin/matching-quality` 看 `share_below_45/47/50`、桌型、到场与氛围；顺序为 staging → 单个无 bot 的生产测试池 → 经单独评审的 global，具体 go/no-go 见 `.git/.orchestration/sprints/sprint-contract.d3-pair-floor.md`。
