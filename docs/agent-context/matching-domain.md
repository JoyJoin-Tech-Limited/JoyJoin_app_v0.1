# Matching Domain — Agent Context

> Extracted from AGENTS.md §6 (2026-07-31). Load when touching pool matching, pair/group formation, match explanation, or test-mode matching. Skill: `matching-domain`.

**Matching:** `poolMatchingService.ts` is deterministic authority. 6D scoring (chemistry, interest, socialAffinity, backgroundDiversity, preference, language). Optional 7th semantic dimension behind `ENABLE_SEMANTIC_SIMILARITY`. AI may enrich explanations but **must not** redefine scoring. Feature-flagged operator-review gate (`matchingOperatorReviewEnabled`) holds formed groups in a pending admin-review state before post-match side effects run; users continue to see the normal pending flow until an operator approves. **Explanation normalization (2026-07-13):** `matchExplanationService.ts::normalizePairExplanationText` is the authoritative normalizer applied at generation (`parsePairExplanationContent`), persist (`savePairExplanationsCache`), and serve (`generateGroupAnalysis` — legacy cached rows cleaned on read), guaranteeing stored/served explanations are plain text, never `{`/`[`-leading (the old catch fall-through had persisted truncated/fenced LLM JSON verbatim). Generation-boundary salvage logs `logger.warn('[MatchExplanation] recovered malformed explanation payload', { promptVersion: 'pair-explanation-v2', kind: truncated|fenced|nested|missing-key, recoveredLength })`; serve/persist paths stay silent. Client defense-in-depth: `normalizeMatchingCopy` (`packages/shared/src/features/matching-status/viewModels.ts`, `unwrapTruncatedJsonWrapper` + `extractReadableText` recursion guard) never returns `{`/`[`-leading strings at any nesting depth. Cache: `event_pool_groups.pair_explanations_cache` (JSONB), 7-day TTL. **Gender-balance enforcement (wired 2026-07-14):** previously inert `event_pools` columns are live — `genderBalanceMode` (`none`/`soft`/`hard`, default `soft`), `genderBalanceBonusPoints` (0–100), `minFemaleCount`/`minMaleCount` (0–20). Soft = post-clamp bonus in `calculateGroupDiversity` for exact male/female balance (default-ON is intended 1:1 policy, never blocks formation); hard = floor gate at group commit and in **all three** redistribution phases (failing groups discarded, members returned to candidate pool; floors hard-mode-only; undisclosed gender counts toward neither floor). `genderRestriction="女性"` implies mode `none`. Admin portal pool create/edit (`性别平衡` section) enforces identical POST/PATCH validation (`insertEventPoolSchema.extend` + `updateEventPoolSchema`); PATCH is audit-logged. Spec: `docs/systems/MATCHING_ALGORITHM_REFERENCE.md` §4.2.1.

**Operator-review-gate unmatched bug fix (2026-07-31, commit `e68edc5e8`):** with `matchingOperatorReviewEnabled=true`, `saveMatchResults` step 2 sets matched members to `matchStatus='pending'`, then step 5 marked **all** `'pending'` registrations `'unmatched'` — flipping the just-formed group's members to unmatched (group-fill 0/0, empty 足迹, confirm-attendance 找不到组; also made a formed matching-test group vanish). Step 5 now only marks the truly stranded (`assignedGroupId IS NULL`). Regression lock: `poolMatchingUnmatchedGuard.test.ts`. Note: code default `getFeatureFlag('matchingOperatorReviewEnabled', false)` is `false` but DB/staging run `true`.

**足迹 one-card-per-matched-pool (2026-07-31):** a matched pool dual-writes a legacy `events` row (`<pool> - 第N组`) + per-member `event_attendance` at match-commit (`saveMatchResults` step 2.5) / single-test finalization, and `getUserJoinedEventsSummary` concatenated legacy + pool rows with no dedup — so one matched pool showed a duplicate legacy card whose `events.id` has **no serving detail endpoint** (`loadEventDetail` only handles `/api/event-pools/:id` and `/api/blind-box-events/:id` → 404「加载活动详情没成功」). `joinedEventsRepo` legacy branch now `LEFT JOIN eventPoolGroups ON eventId` and keeps only `IS NULL` (drops match-derived legacy cards; standalone legacy events unaffected). Each matched pool yields one servable pool card. Regression lock: `joinedEventsRepoContract.test.ts`.

**Matching-Test Mode (2026-06-24; updated 2026-07-26):** End-to-end matching validation with one real tester + full-profile bot users through the **same production matching engine**. Defense-in-depth isolation: `isMatchingTestMode()` double gate (requires `ENABLE_SINGLE_TEST_MODE` + `ENABLE_MATCHING_TEST_MODE`; returns false in `APP_MODE=production`), DB markers `users.is_test_bot` + `event_pools.is_test_pool`, and a startup sentinel that crashes if test-bot rows exist in production. Routes at `/api/test/matching-test/*` (start, match, cleanup). Service at `apps/server/src/services/matchingTestService.ts`. Bot profiles include archetypes, industry tiers, `user_interests`, and registration preferences so `poolMatchingService` can score them identically to real users. Groups are finalized into `events`/`blindBoxEvents`/`eventAttendance`/`venueTimeSlotBookings` via `matchingTestService.ts:finalizeTestPoolGroups()` (also reused by `singleTestService.ts`) so post-match flows (event detail, confirm-attendance) work end-to-end. Cleanup preserves payment records. **Test pools are exempt from the registration capacity gate (2026-07-31):** single-test sessions register tester + 5 bots, filling the pool to exactly `maxGroupSize × targetGroups` (6/6) by design — `describePoolRegistrationAvailability` (`apps/server/src/lib/poolRegistrationRules.ts`) skips the `POOL_FULL` check when `event_pools.is_test_pool=true` (threaded through `/register`, `/register-with-payment`, and `payments.ts:resolveEventCheckout`), and the pool_full notification/WS broadcast is skipped for test pools. Real event pools keep the full capacity rule (queues may exceed 6; matching forms groups of 4-6). Regression lock: `poolRegistrationRules.test.ts`. **Test-mode cleanup FK cascade (2026-07-31, commit `675ac3624`):** `cleanupSingleTestData` and `cleanupMatchingTestData` used to enumerate child tables by hand before deleting virtual users / test bots, which repeatedly missed new FK dependents (`event_pool_registrations`, `blind_box_events`, etc.) and failed with FK violations. `apps/server/src/lib/fkCascadeDelete.ts` now provides `cascadeDeleteByIds(tx, rootTable, rootColumn, rootIds)` which discovers non-`ON DELETE CASCADE` foreign keys from `pg_constraint` at runtime, recurses deepest-first, and deletes transitive dependents automatically. Future schema additions are covered without code changes. Safety rails: UUID-only root IDs (injection guard), ignores existing `ON DELETE CASCADE` edges (left to Postgres), depth cap + visited-edge set prevents runaway/cycles, schema-qualified table names are taken verbatim from Postgres, columns are quoted. Note: it only walks dependencies that point **at** the root table; reverse references (e.g. `eventPoolGroups.eventId → events.id` from derived legacy events) still require explicit back-link cleanup as in `cleanupSingleTestPoolRows`. Regression lock: `apps/server/src/__tests__/fkCascadeDeleteContract.test.ts`. **Social Icebreaker test mode** is a single-player variant for QA/demoing the session flow: `TestModeDisclosure` pauses the host in `warmup`, and deterministic bot simulation (`apps/server/src/services/socialIcebreakerBotService.ts`) populates all multiplayer phases when `runBots === true`. Docs: `docs/operations/test-mode-operations.md` §H and §I.
